# Маршруты и политики

**Русский** | [English](ROUTING.en.md)

## Только выбранные адреса через VPN

1. Провайдер первым, VPN ниже в политике по умолчанию.
2. Компьютер и сегмент «Основной» остаются в политике по умолчанию.
3. Нет включённого пользовательского маршрута `По умолчанию → VPN`.
4. Загрузите свой `.bat` через «Маршрутизация → Загрузить», выбрав интерфейс VPN. Не запускайте `.bat` на Windows.

Пример формата (документационный адрес, замените нужной сетью):

```text
route ADD 192.0.2.0 MASK 255.255.255.0 0.0.0.0
```

Указанные назначения идут через туннель, остальные — через провайдера, с учётом других маршрутов. AllowedIPs `0.0.0.0/0` можно сохранить в AWG: это разрешение передавать любые IPv4 внутри туннеля, а путь выбирается таблицей маршрутов.

Списки Amazon/Cloudflare включают множество сторонних сайтов. IP меняются; название файла не гарантирует полноту списка. Автообновление списков не реализовано. Пользовательские IP-списки не поставляются с проектом.

IPv6 этими маршрутами не управляется. Проверка с `curl -4` относится только к IPv4.

## Всё устройство через VPN

Провайдер остаётся первым в системной политике. Одному тестовому устройству назначается отдельная политика с VPN. Для full-tunnel явно зарегистрируйте default route туннеля (подставьте свой номер):

```sh
ndmc -c "ip route default OpkgTun0"
```

После команды проверьте, что системный default остался через провайдера, а Endpoint не направлен внутрь собственного туннеля:

```sh
ip -4 route show table all
ip -4 route get АДРЕС_VPN_СЕРВЕРА
```

В последней команде замените текст реальным IPv4. Если default переключился на VPN, восстановите приоритет провайдера. WAN IPv4 может меняться после переподключения: нельзя брать старый адрес из чужой инструкции.

Политика только с VPN означает отсутствие резерва. Для разрешённого обхода через WAN провайдер должен входить в политику и нужен контроль доступности. Чтобы исключить обход через IPv6, отключите IPv6 на тестовом устройстве или сегменте: эта обвязка не реализует IPv6 kill switch.

«Основной» — домашний сегмент, не сам роутер. У клиентов с явной политикой она имеет приоритет над наследованием сегмента. Службы роутера используют системную маршрутизацию; отдельные маршруты и DNS-привязки могут её уточнять.

## Переход обратно к выборочным IP

Верните устройство в системную политику с первым провайдером. Отключите пользовательский маршрут «По умолчанию → VPN» в веб-интерфейсе или удалите командой:

```sh
ndmc -c "no ip route default OpkgTun0"
```

На тестовом устройстве команда однажды вернула `file exists`, хотя маршрут исчез. Проверяйте таблицу после ошибки, не повторяйте изменения вслепую. Не используйте «удалить все маршруты интерфейса», если там уже импортирован нужный список.

## Проверка с компьютера

PowerShell, VPN-приложение выключено, политика назначена этому устройству:

```powershell
ping -4 -n 4 8.8.8.8
nslookup example.com
curl.exe -4 --connect-timeout 10 --max-time 20 https://example.com/
```

Проверьте внешний IP на нужном пути. Ping до DNS с отдельным маршрутом не доказывает работу всего full-tunnel. При выборочных маршрутах сайт проверки IP может правильно показывать провайдера.

DNS из профиля привязывается к VPN через `ip name-server ... on OpkgTunN`. Прошивка может создать отдельный маршрут к этому DNS — например, 1.1.1.1 продолжит идти через VPN даже при первом провайдере. Учитывайте это при диагностике; после сбоя VPN отдельно проверяйте разрешение имён.
